# Bank lines are synthesised to Razorpay's schema, and the recon breakdown is never consumed

Razorpay's Settlements API and its recon endpoint (`GET /v1/settlements/recon/combined`) are
callable with test keys, but nothing in the documentation says test mode *generates*
settlements — settlement is a real banking cycle driven by real money movement, and none moves
in test mode. So §5.9a's bank lines are generated by us.

They conform to Razorpay's actual settlement entity — `id`, `amount`, `status`, `fees`, `tax`,
`utr`, `created_at` — so the matcher reads the same fields it would read in production.

**We deliberately do not feed the recon breakdown to the matcher.** The recon endpoint returns
the constituent rows of a settlement — `settlement_id`, `payment_id`, `type`, `amount` — which
is the answer key. Consuming it would make matching arithmetic we already know the result of.
The matcher receives only the bank line (amount, UTR, date) and reconstructs the decomposition
from receipts the Desk signed (FR-7.2).

## Consequences

Say this plainly rather than letting it be discovered: the bank feed is a fixture, because test
mode does not settle. The claim that survives is the narrower true one — *given a bank line, the
Desk proves it against its own signed receipts and refuses to count what it cannot prove* — and
that claim is unaffected by who generated the line.

Do not "improve" the matcher by wiring in recon data. It would delete the problem, not solve it.
